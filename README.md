# DocumentChain — реестр студенческих документов на W3C VC 2.0

Децентрализованная система выпуска, хранения и верификации студенческих дипломов и документов в формате **W3C Verifiable Credentials 2.0**. Личные данные студента хранятся исключительно в файле VC на его устройстве — в блокчейн попадают только анонимные технические идентификаторы.

---

## Задача системы

Традиционные бумажные или централизованные электронные документы сложно верифицировать независимо: нужно обращаться к источнику, который может быть недоступен или ненадёжен. Эта система позволяет:

- выпускать подписанное машиночитаемое свидетельство о документе (VC);
- хранить его локально у студента в виде JSON-файла;
- проверять подлинность в любой момент по подписи, блокчейну и оригинальному PDF.

Никакого центрального хранилища данных не требуется. Верификация работает офлайн для части проверок и через публичный блокчейн Sepolia для остальных.

## Архитектура

### Модель идентификаторов (DID)

Каждый участник идентифицируется через адрес кошелька MetaMask:

```
did:pkh:eip155:11155111:<ethereum_address>
```

Один DID = один активный документ. Повторная выдача возможна только после отзыва предыдущего.

### W3C Verifiable Credential 2.0

VC — это JSON-LD объект со следующей структурой:

```json
{
  "@context": [
    "https://www.w3.org/ns/credentials/v2",
    "https://w3id.org/security/suites/secp256k1recovery-2020/v2"
  ],
  "id": "0x<credentialId>",
  "type": ["VerifiableCredential", "DocumentCredential"],
  "issuer": { "id": "did:pkh:eip155:11155111:<issuer>" },
  "validFrom": "2024-...",
  "validUntil": "2027-...",
  "credentialSubject": {
    "id": "did:pkh:eip155:11155111:<holder>",
    "studentName": "...",
    "documentNumber": "...",
    "institution": "...",
    "issueDate": "...",
    "degree": "...",
    "fileHash": "0x<sha256_of_pdf>"
  },
  "proof": {
    "type": "EcdsaSecp256k1RecoverySignature2020",
    "proofValue": "0x<signature>"
  }
}
```

Формат доказательства: **EcdsaSecp256k1RecoverySignature2020** — подпись через `personal_sign` MetaMask, проверяется через `ethers.verifyMessage()`.

### Что хранится где

| Данные | Хранение |
|--------|----------|
| Полный VC (ФИО, номер диплома, степень) | Off-chain — JSON-файл у студента |
| Кэш VC для UX | Off-chain — IndexedDB браузера |
| Реестр доверенных эмитентов | On-chain — смарт-контракт |
| Статус отзыва по `credentialId` | On-chain — смарт-контракт |
| `credentialId → issuer`, `holder → credentialId` | On-chain — смарт-контракт |

**PII (персональные данные) в блокчейн не попадают никогда.**

### Смарт-контракт `VCRegistry`

Хранит только:
1. Реестр доверенных адресов-эмитентов (`isIssuer`)
2. Маппинг `credentialId → адрес эмитента`
3. Маппинг `credentialId → флаг отзыва`
4. Маппинг `holder → текущий credentialId` (ограничение «один документ»)

`credentialId` вычисляется детерминированно:
```
keccak256(abi.encodePacked(issuerAddress, holderAddress, fileHashBytes32))
```

### Роли и права

| Роль | Описание | Что может делать |
|------|----------|-----------------|
| **Owner (владелец)** | Адрес, задеплоивший контракт | Добавлять/удалять эмитентов; аварийно отзывать любой VC |
| **Issuer (эмитент)** | Адрес из белого списка owner | Выпускать VC, регистрировать `credentialId`, отзывать свои VC |
| **Holder (студент)** | Адрес, указанный эмитентом как получатель | Хранить и предъявлять VC-файл |
| **Verifier (верификатор)** | Любой пользователь | Загружать VC + PDF и проверять подлинность |

## Как работает система

### Выпуск VC (роль: Эмитент)

1. Эмитент открывает вкладку «Для эмитента» и подключает MetaMask.
2. Загружает PDF-документ студента — браузер вычисляет SHA-256 через Web Crypto API.
3. Заполняет поля: ФИО студента, номер документа, учреждение, дата, специальность.
4. Указывает адрес кошелька студента (holder).
5. **Шаг 1/3** — вычисляется `credentialId`, строится VC-пэйлоад без `proof`, MetaMask запрашивает подпись (`personal_sign`).
6. **Шаг 2/3** — подписанный `credentialId` регистрируется on-chain через `registerCredential()`.
7. **Шаг 3/3** — браузер сохраняет подписанный JSON-файл VC (`credential-<id>.json`) на устройство студента.

> VC дополнительно кэшируется в IndexedDB на случай, если студент не успел сохранить файл.

### Хранение VC (роль: Студент)

- Первичное хранилище — файл на устройстве студента.
- Вторичное хранилище — IndexedDB в браузере (автоматически).
- `localStorage` не используется.

### Проверка VC (роль: Верификатор)

1. Верификатор загружает JSON-файл VC и оригинальный PDF.
2. Система выполняет 5 независимых проверок:

| # | Проверка | Метод |
|---|---------|-------|
| 1 | Подпись | `ethers.verifyMessage(canonical_vc_без_proof, proofValue)` == адрес эмитента |
| 2 | Доверенный эмитент | `contract.isIssuer(issuerAddress)` == `true` |
| 3 | Не отозван | `contract.checkRevocation(credentialId)` == `false` |
| 4 | Не просрочен | `vc.validUntil > now` |
| 5 | Совпадение файла | `SHA-256(pdf)` == `credentialSubject.fileHash` |

Итог `valid: true` — только если все 5 проверок пройдены.

### Отзыв VC (роль: Эмитент или Owner)

- Эмитент может отозвать VC, которую сам выпустил.
- Owner может аварийно отозвать любую VC (на случай компрометации ключа эмитента).
- После отзыва студент может получить новый VC (ограничение «один документ» снимается).

## Порядок запуска

### 1. Установка зависимостей

```bash
cd vkr_project
npm install
```

### 2. Настройка переменных окружения

Создать файл `vkr_project/.env`:

```
INFURA_URL=https://sepolia.infura.io/v3/<YOUR_PROJECT_ID>
PRIVATE_KEY=<0x_private_key_of_deployer>
INITIAL_ISSUER=<0x_address_of_first_issuer>
```

> **Важно:** `PRIVATE_KEY` — это ключ кошелька, который станет owner контракта. Никогда не коммитьте этот файл.

### 3. Компиляция контракта

```bash
cd vkr_project
npx hardhat compile
```

### 4. Деплой на Sepolia

```bash
cd vkr_project
npx hardhat run scripts/deploy.js
```

После деплоя — скопировать адрес контракта из вывода и вставить в `website/index.html`:

```javascript
const contractAddress = "0x<deployed_address>";
```

Текущий адрес в `index.html`: `0xb6e604b7e78544656Ef36DE86b05611b75231595`

### 5. Запуск тестов

```bash
cd vkr_project
npm test
```

Или отдельно:
```bash
npx hardhat test test/DocumentRegistry.test.js   # тесты контракта
npx hardhat test test/vc-layer.test.js           # тесты VC-слоя
```

### 6. Открытие frontend

Открыть `website/index.html` напрямую в браузере или через любой статический сервер:

```bash
npx serve website
# или
python3 -m http.server 8080 --directory website
```

Подключить MetaMask к сети **Sepolia**. При открытии на неправильной сети приложение предложит переключиться автоматически.

## Важные ограничения

- **Один DID = один документ.** Повторная выдача VC одному студенту возможна только после отзыва предыдущей.
- **VC хранится у студента.** Если студент потерял файл и кэш IndexedDB очищен, VC не восстановить (эмитент может выпустить новый после отзыва).
- **Нет бэкенда.** Все операции выполняются в браузере; для транзакций нужен MetaMask.
- **Только Sepolia.** Контракт задеплоен в тестовой сети. На mainnet это приложение не рассчитано.
- **DID-метод:** строго `did:pkh:eip155:11155111:<address>` — другие методы не поддерживаются.
- **Формат доказательства:** строго `EcdsaSecp256k1RecoverySignature2020` — смешение форматов не допускается.

## Безопасность и ограничения

### Что делает система

- Криптографически привязывает PDF-документ к конкретному студенту через SHA-256 + подпись.
- Подтверждает, что VC был выпущен доверенным эмитентом из белого списка контракта.
- Позволяет владельцу контракта аварийно отозвать VC при компрометации ключа эмитента.
- Не позволяет одному студенту иметь два активных документа одновременно.

### Чего система не делает

- Не идентифицирует личность студента (не верифицирует, что `studentName` в VC соответствует реальному человеку).
- Не защищает от того, что эмитент выпустит VC с неверными данными — доверие к эмитентам лежит на стороне owner.
- Не гарантирует доступность Infura-эндпоинта для проверки.
- Не является юридически признанной электронной подписью.

### Что не должно попадать в блокчейн

В соответствии с архитектурным решением, в транзакциях и хранилище контракта **никогда** не должны появляться:

- ФИО студента
- Номер документа
- Название учебного заведения
- Дата выдачи
- Степень / специальность
- Полный payload VC
- Хеш файла отдельно (он уже закодирован внутри `credentialId`)
